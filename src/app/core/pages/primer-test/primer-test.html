Buscamos cubrir riesgos.

Testeamos comporamiento, reglas de negocio y casos límite, no detalles internos.

Evitamos tests redundantes

El primer test: scripts ad-hoc y validación manual

En los primeros días, los tests eran scripts improvisados que manipulaban el DOM y verificaban resultados con console.assert o inspección visual. Eran frágiles, lentos y con cobertura limitada.

2. Test de lógica de negocio y validación de entrada

En una app real, el descuento suele venir de un formulario y llega como texto. Por eso, en vez de pensar en 20% como argumento literal (en JavaScript eso ni siquiera compila), se valida y normaliza el dato antes de calcular.

Este ejemplo es mejor que una suma simple porque combina negocio + validación de entrada y refleja un error típico: equivocarse al pasar argumentos o recibir formatos inesperados.

¿Dónde validar?

En ambos sitios: en la UI (feedback temprano) y en la función (defensa final).

¿Se valida todo siempre?

No con la misma profundidad. Prioriza funciones críticas, fronteras de entrada y zonas de alto riesgo de regresión.

¿Código o tests?

Primero el código define reglas y errores; después los tests prueban casos felices, límites y formatos inválidos para garantizar el contrato.

3. Test de comportamiento con edge cases

Aquí aparece un concepto crítico del testing: los casos límite y situaciones inesperadas.

Un buen test no solo valida el camino feliz; también protege el sistema ante entradas incompletas o inválidas.

4. Test que detecta un bug real

Este ejemplo demuestra por qué testear aporta valor real: los tests pueden revelar bugs ocultos.

Aquí aparece el bug real: indexOf devuelve -1 y splice(-1, 1) elimina el último elemento. Este tipo de hallazgo es exactamente lo que justifica invertir en tests.
