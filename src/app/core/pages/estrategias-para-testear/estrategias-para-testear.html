Estrategias para testear correctamente

Una buena batería de tests protege lo importante: el comportamiento visible, las reglas de negocio, las integraciones y los casos límite. No intentamos testear cada detalle interno del código. En esta página verás ejemplos concretos de lo que sí merece una prueba y de lo que conviene evitar por frágil o redundante.

Qué suele merecer un test

Cuando priorizas bien, los tests ayudan a detectar errores pronto y a refactorizar con confianza. Lo más valioso suele ser cubrir resultado visible, reglas, dependencias y bordes.

Flujos del usuario

Qué pasa al enviar un formulario, pulsar un botón o completar un proceso importante. Si el usuario lo nota, suele merecer un test.

Reglas de negocio

Descuentos, validaciones, permisos, cálculos o decisiones del dominio. Aquí viven muchos bugs caros.

Integraciones

APIs, storage, router o servicios externos. No se testea la librería en sí, sino cómo nos integramos con ella.

Casos límite y errores

Entradas inválidas, listas vacías, null, estados de carga o datos corruptos. Son situaciones pequeñas que suelen romper mucho.

Qué no conviene priorizar

No todo test aporta el mismo valor. Algunos son tan frágiles o tan internos que solo generan ruido al mantenerlos.

Detalles internos

No interesa fijarse en si una función usa map, trim o una variable concreta si el resultado final es correcto.

Duplicados

Varios tests que garantizan exactamente lo mismo encarecen mantenimiento sin aumentar confianza real.

Frameworks o librerías ajenas

No testees que Angular renderiza un input o que el navegador ejecuta un click. Testea tu contrato con esas piezas.

Visuales incidentales

No suele compensar fijar colores, orden interno o clases CSS exactas si no forman parte del comportamiento que quieres proteger.

Ejemplo 2. Reglas de negocio y caso límite

Este tipo de test sí aporta mucho valor porque protege decisiones reales del negocio: cuándo el envío es gratis y qué pasa con entradas inválidas.

Aquí el valor del test no está en cubrir líneas, sino en dejar explícito un contrato: qué se cobra, cuándo y cómo falla.

Qué protege

La regla del envío gratis y el rechazo de valores imposibles.

Qué caso borde cubre

Un total negativo, que podría colarse por un bug en otra capa.

Por qué merece quedarse

Porque protege decisiones de negocio que sí afectan al usuario y al sistema.

Ejemplo 4. Un test que conviene evitar

No todo lo que puede comprobarse merece una prueba. Un test que inspecciona la implementación interna suele romperse en refactors aunque el comportamiento siga siendo correcto.

Test útil

Comprobar el resultado final que ve o consume otro código.

Test frágil

Comprobar si la función usa una API concreta o una estrategia interna determinada.

Regla práctica

Si puedes refactorizar por dentro sin romper el contrato, ese detalle no debería fijarlo un test.

Guía rápida para decidir

Sí lo testearía si...

Romperlo afectaría al usuario, al negocio o a una integración crítica.

No lo priorizaría si...

Solo asegura una decisión interna de implementación que puede cambiar mañana.

¿Qué riesgo real cubre este test? Si no sabes responder, quizá no merece quedarse.
